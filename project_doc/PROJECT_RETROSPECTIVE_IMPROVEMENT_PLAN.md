# AtomicProof Compiler 项目复盘与改进计划

生成日期：2026-05-22

## 项目背景

AtomicProof Compiler 是一个面向 UTXO / BVM 双栈虚拟机的 `.ct` 智能合约编译器，目标是用类 Python 语法、静态类型和编译期所有权检查，降低原生比特币脚本难写、难测、难调试的问题。

目前项目已完成 Lexer、Parser、AST、多 Pass 编译管线、字节码生成、结构化错误处理、BVM 模拟器和 CLI 调试器框架，并配套了中英文文档、标准库、133 个 `.ct` 测试/示例和 16 个 sCrypt 改写对照合约。当前构建、基本编译和调试信息生成均已验证通过。

后续主要问题包括：补齐可复现 benchmark、完善调试器稳定性、同步文档与版本能力描述，并对字节码体积、编译时间、错误检出率等指标形成系统评测数据。

## 1. 项目存在的主要不足

### 1.1 目标设定不足：缺少可量化的发布标准

项目已经完成了多个核心模块，但当前的目标描述仍偏向“功能已实现”或“流程已跑通”，尚未转化为明确的版本验收标准。例如：

- 支持多少语言特性才算达到 `v0.1-alpha`。
- 133 个 `.ct` 示例中有多少必须稳定编译通过。
- 16 个 sCrypt 改写合约需要达到怎样的语义对照完整度。
- 字节码体积、编译时间、错误定位准确率需要达到什么阈值。
- CLI 调试器哪些命令必须可用、稳定、可自动化回归。

如果缺少这些标准，项目很容易出现“开发完成度较高，但无法判断是否可以发布”的问题。

### 1.2 执行过程不足：功能推进快，系统性验证滞后

项目在 Lexer、Parser、AST、编译 Pass、字节码生成、错误处理、BVM 模拟器等方面进展较快，但 benchmark、错误检出率、调试器稳定性和用户任务验证仍处于待补齐状态。

这说明项目已经形成了较完整的技术骨架，但质量验证体系还没有完全跟上工程实现速度。

### 1.3 时间安排不足：性能、调试器、文档同步被后置

Benchmark、调试器稳定性和文档同步通常容易被视为后期收尾工作，但对编译器项目来说，它们直接影响可用性、可信度和外部采用意愿。

如果这些工作集中到发布前处理，可能导致以下问题：

- 性能数据不足，无法说明项目相对原生脚本或 sCrypt 改写方案的优势。
- 调试器在复杂合约下不稳定，影响开发者首次体验。
- 文档描述超前于实际能力，引发用户误解。
- 临近发布时发现关键能力缺口，导致版本延期。

### 1.4 资源配置不足：缺少明确的质量、性能、文档责任角色

项目涉及编译器前端、编译管线、字节码生成、虚拟机模拟、CLI 调试器、标准库、文档、测试样例和 sCrypt 对照合约，技术跨度较大。

如果由少数开发者同时承担核心研发、测试、文档和发布管理，容易导致以下短板：

- 性能评测无人持续维护。
- 调试器体验缺少专门打磨。
- 文档更新滞后于实现。
- 风险清单和发布检查缺少固定负责人。

### 1.5 团队协作不足：跨模块接口契约不够清晰

多 Pass 编译管线、AST、错误系统、字节码生成、BVM 模拟器和 CLI 调试器之间存在强依赖。如果缺少明确的接口契约，后续容易出现以下问题：

- 某个 Pass 修改 AST 或中间表示后，错误定位和调试信息失效。
- 字节码生成规则变化后，BVM 模拟器或调试器没有同步更新。
- 所有权检查、类型检查和错误系统之间的责任边界不清。
- 新增语言特性时，测试和文档不知道应覆盖哪些模块。

### 1.6 成果质量不足：缺少系统评测数据支撑项目价值

项目目标是降低原生比特币脚本难写、难测、难调试的问题，但当前仍缺少系统化数据证明这些价值。例如：

- 与原生 Bitcoin Script 或 sCrypt 改写版本相比，代码量减少多少。
- 编译后字节码体积是否可控。
- 编译时间是否随合约复杂度线性或可接受增长。
- 错误信息是否能准确定位到源代码行列。
- 调试器是否能有效缩短问题定位时间。

缺少这些数据，会削弱项目对外展示、论文撰写、技术推广和版本发布的说服力。

### 1.7 用户反馈不足：缺少真实使用者闭环

当前已有较多 `.ct` 测试和示例，但内部测试不等同于真实用户验证。真实开发者可能会在以下环节遇到问题：

- 不知道如何从文档开始完成第一个合约。
- 对所有权检查报错原因理解困难。
- 调试器命令使用成本高。
- 迁移 sCrypt 合约时不知道能力边界。
- 标准库能力和示例覆盖不足。

项目还需要通过任务式试用收集外部反馈，而不只依赖内部样例通过率。

### 1.8 风险控制不足：编译正确性和安全语义风险需要显式管理

智能合约编译器的风险不只是程序崩溃，还包括错误编译、语义偏差、安全检查遗漏和调试误导。当前需要重点管理以下风险：

- 类型检查通过但生成字节码语义错误。
- 所有权检查遗漏导致状态或资产约束表达不完整。
- BVM 模拟结果和实际执行环境存在差异。
- 调试信息行列映射错误，误导开发者定位问题。
- 标准库行为与文档描述不一致。
- 字节码体积或编译时间在复杂合约中不可控。

## 2. 不足产生的原因

| 不足项 | 可能原因 |
|---|---|
| 缺少量化发布目标 | 前期重点放在核心编译链路跑通，尚未把研发目标转化为版本发布指标 |
| 系统性验证滞后 | 测试更多覆盖语法、样例和基本编译，缺少性能、错误检出率、调试器稳定性的专项验证 |
| 性能、调试器、文档同步被后置 | 这些工作容易被当作发布收尾事项，但实际属于开发者体验和可信度建设 |
| 资源角色不清 | 项目技术面较宽，核心开发者可能同时承担实现、测试、文档和发布工作 |
| 跨模块协作成本高 | 编译管线模块多，Pass、错误系统、调试器和字节码生成之间缺少稳定契约文档 |
| 评测数据不足 | 尚未建立固定 benchmark 集、基线版本、自动化运行脚本和结果报告格式 |
| 用户反馈不足 | 当前验证偏内部样例和测试，缺少外部开发者基于任务的独立试用 |
| 风险控制不显式 | 编译正确性、安全语义、UTXO/BVM 双栈一致性风险需要专门台账和回归机制 |

## 3. 改进方向

### 3.1 建立版本发布门槛

为 `v0.1-alpha` 定义硬性发布指标，包括：

- 133 个 `.ct` 测试/示例必须全部可编译，失败项必须有明确原因和 issue。
- 16 个 sCrypt 改写合约必须有语义对照说明、输入输出样例和差异说明。
- CLI 调试器必须稳定支持断点、单步、查看栈、查看变量、错误定位映射等核心命令。
- 中英文文档必须与当前版本能力一致。
- benchmark 报告必须包含编译时间、字节码体积、Pass 耗时和回归对比。

### 3.2 建设可复现 benchmark

建立固定 benchmark 合约集，覆盖以下类型：

- 简单转账。
- P2PKH。
- 多签。
- 时间锁。
- 条件锁。
- 原子交换。
- 预言机合约。
- 状态机合约。
- 标准库调用。
- 复杂控制流。
- 数组、结构体和复合类型。
- sCrypt 改写对照合约。

每次 benchmark 输出固定格式报告，至少包含：

- 合约名称。
- 源码行数。
- 编译耗时。
- 各 Pass 耗时。
- 生成字节码体积。
- 编译错误或警告数量。
- 相对上一次基线的变化百分比。

### 3.3 把调试器稳定性纳入 CI

为 CLI 调试器建立脚本化会话测试，覆盖：

- 启动调试。
- 设置断点。
- 单步执行。
- 继续执行。
- 查看栈。
- 查看变量。
- 查看当前指令。
- 异常路径定位。
- 源码行列映射。
- 非法命令和边界输入处理。

验收目标是核心命令自动化测试通过率达到 100%，异常路径不少于 10 个 case。

### 3.4 建立文档与能力矩阵

在中英文文档中增加“当前版本能力矩阵”，按以下状态标注：

- 已支持。
- 部分支持。
- 实验性支持。
- 未支持。
- 计划支持。

能力矩阵至少覆盖：

- 语言语法。
- 类型系统。
- 所有权检查。
- 内置函数。
- 内置对象。
- 标准库。
- CLI 命令。
- 调试器能力。
- BVM 模拟器能力。
- 与 sCrypt 对照迁移相关的限制。

### 3.5 强化编译正确性验证

新增负向测试集，覆盖：

- 语法错误。
- 类型错误。
- 所有权错误。
- 未定义变量。
- 函数调用参数不匹配。
- 数组越界相关静态诊断。
- 结构体字段错误。
- 未支持语言特性。
- 标准库误用。
- 字节码生成前置条件不满足。

每个负向测试都要校验错误码、错误信息、源代码行列和建议修复方向。

### 3.6 引入用户任务式试用

设计 5 个真实任务，让 3-5 名开发者独立完成：

- 从零编写一个 P2PKH 合约。
- 将一个简单 sCrypt 合约改写为 `.ct`。
- 根据错误信息修复一个类型错误。
- 使用 CLI 调试器定位一个栈或变量问题。
- 根据文档完成一次合约测试流程。

记录每个任务的完成时间、失败点、文档卡点、错误信息理解成本和用户建议。

### 3.7 建立风险清单和发布检查表

风险分为六类：

- 编译正确性风险。
- BVM 行为一致性风险。
- 调试器定位风险。
- 标准库行为风险。
- 文档误导风险。
- 性能退化风险。

每个风险项必须包含负责人、影响范围、触发条件、缓解措施、验证方式和当前状态。

## 5. 阶段性行动计划

### 5.1 短期计划：2026-05-22 至 2026-06-07

#### 要做什么

- 完成 `v0.1-alpha` 发布标准。
- 建立项目风险清单。
- 建立中英文文档能力矩阵。
- 确定 benchmark 合约集。
- 确定负向测试集目录和用例范围。

#### 怎么做

- 将现有能力拆成四张清单：语言特性、编译管线、CLI 调试器、标准库/BVM 能力。
- 每项能力标注支持状态、测试覆盖状态和文档状态。
- 选定至少 20 个 benchmark case，覆盖基础合约、复杂控制流、标准库调用和 sCrypt 改写对照。
- 设计至少 80 个负向测试 case，覆盖语法、类型、所有权、标准库误用和未支持能力。
- 建立风险台账，按风险类别分配负责人和验证方式。

#### 完成标准

- `v0.1-alpha` 发布清单完成，并经过一次评审。
- 中英文文档能力描述一致，无明显超前描述。
- benchmark case 列表完成，且每个 case 有用途说明。
- 负向测试 case 列表完成，且每类错误至少有代表样例。
- 高风险项均有负责人、缓解措施和验证方式。

### 5.2 中期计划：2026-06-08 至 2026-07-10

#### 要做什么

- 补齐自动化 benchmark。
- 补齐调试器稳定性测试。
- 完成错误检出率评测。
- 完成 16 个 sCrypt 改写合约对照报告。
- 固化发布回归流程。

#### 怎么做

- 将 benchmark 接入 CI，每次运行输出 JSON 和 Markdown 两种格式报告。
- 调试器使用脚本化会话测试核心命令和异常路径。
- 负向测试校验错误码、错误信息、行列定位和修复建议。
- 对 16 个 sCrypt 改写合约逐一补充语义说明、输入输出样例、差异说明和限制条件。
- 发布前统一运行示例编译、单元测试、调试器测试、benchmark 和文档检查。

#### 完成标准

- 至少 20 个 benchmark case 可一键运行。
- benchmark 报告包含编译时间、字节码体积、Pass 耗时和基线对比。
- CLI 调试器核心命令自动化测试通过率达到 100%。
- 异常路径测试不少于 10 个 case。
- 负向测试不少于 80 个。
- 错误定位行列准确率不低于 95%。
- 16 个 sCrypt 对照合约均有可复现实验记录。
- 发布候选报告可以一键生成，阻塞项为 0 才允许发布。

### 5.3 长期计划：2026-07-11 至 2026-08-31

#### 要做什么

- 完成外部用户任务式试用。
- 建立持续质量看板。
- 根据反馈修复高优先级问题。
- 形成稳定版本迭代机制。

#### 怎么做

- 邀请 3-5 名开发者独立完成 5 个任务：编写 P2PKH 合约、迁移 sCrypt 合约、修复类型错误、使用 CLI 调试器定位问题、根据文档完成合约测试流程。
- 记录每个任务的完成时间、失败点、文档卡点、错误信息理解成本和用户建议。
- 每周更新质量看板，跟踪编译成功率、字节码体积变化、编译时间变化、错误检出率、调试器失败率和文档问题数量。
- 将用户反馈按高、中、低优先级分类，优先修复阻塞首次使用和影响编译正确性的问题。

#### 完成标准

- 完成一次 `v0.1-alpha` 发布候选流程。
- 收集不少于 15 条有效用户反馈。
- 高优先级反馈修复率不低于 80%。
- 质量看板连续更新至少 4 周。
- 后续版本能基于指标判断是否可发布，而不是只依赖主观判断。

## 7. 总结

AtomicProof Compiler 当前已经完成了从语言前端到字节码生成、模拟器和调试器框架的主体建设，说明项目已经跨过了“能否实现”的阶段。下一阶段的核心任务应从功能实现转向工程可信度、可复现评测和开发者可用性。

最优先的改进不是继续扩展更多语言特性，而是先建立清晰的发布门槛、benchmark 基线、调试器回归测试、能力矩阵和风险清单。只有这些基础设施补齐后，项目才能更可靠地进入公开试用、论文评估或版本发布阶段。
