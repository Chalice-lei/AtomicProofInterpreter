# 开题报告_徐磊_增补修改建议

生成日期：2026年6月16日

说明：本文件依据《开题撰写培训2025.11.pdf》和《开题报告_徐磊.doc》提取内容形成。原《开题报告_徐磊.doc》未被修改。由于原报告为传统 `.doc` 文件，本文同时参考了转换后的 HTML、PDF 渲染页和正文抽取结果；关于表格跨页、断词等排版问题，建议最终以 WPS 或 Word 直接导出的 PDF 再复核一次。

## 一、总体评价

当前开题报告完成度较高，已经覆盖工程硕士开题报告的主要栏目，包括题目、摘要、选题依据、国内外技术应用现状、技术难度、课题内容、需求分析、概要设计、开发环境、测试方案、本人主要工作、进度安排和预期成果等内容。报告围绕 UTXO 智能合约、BVM 双栈虚拟机、字节码解释执行、AST 源码解释、交易上下文、CLI 调试器和差分测试展开，技术主线比较明确，工程属性也比较突出。

对照培训材料，当前报告的主要短板不是“没有内容”，而是部分内容还没有完全转化为开题审查所期待的论证形态。培训材料强调开题报告应回答“做什么、为什么做、如何做”，并体现工作量、复杂性、专业性、逻辑性和认真态度；工程软件类论文还要求需求分析合理、总体设计正确、程序编制及文档规范，并通过测试或可现场演示。当前报告在“做什么”和“如何做”方面写得较充分，但在工程来源说明、正文引用标注、研究目标的集中表达、创新点提炼、进度细化、预期成果清单和排版规范方面仍需加强。

需要特别注意的是，培训材料明确指出：开题需阅读至少15篇参考文献，其中英文文献至少5篇；国内外概况应体现发展进程、研究方向、近年来发展趋势和最新成果；参考文献引用位置要标注；研究内容及具体方案应包含课题内容、设计方法、技术路线和实验验证方案；时间节点不宜过粗；常见问题包括题目不够简练、摘要不能概括论文工作、背景偏离主题、研究内容不清晰、术语未及时介绍、表格跨页、参考文献不规范、预期成果不足等。当前报告应围绕这些点进行定向修改。

## 二、对照培训材料发现的问题

| 问题位置 | 存在问题 | 培训材料对应要求 | 修改建议 |
|---|---|---|---|
| 论文题目：“一种智能合约高级语言的解释性执行系统的设计与实现” | 题目能够概括“解释性执行系统”，但没有体现报告正文反复强调的 UTXO、双栈虚拟机或 BVM 场景。题目中的“智能合约高级语言”范围偏宽，容易被理解为面向一般智能合约语言，而非面向 UTXO 双栈脚本验证工具链。 | 培训材料第11页要求题目准确、规范，必须把研究问题和研究对象交代清楚，题目要与研究内容一致，不能太大也不能太小。第23页也将“论文题目不够简练，不能准确表达论文工作”列为院审常见问题。 | 建议将题目改为更贴合正文的表述，例如“面向 UTXO 双栈虚拟机的智能合约解释性执行系统设计与实现”或“面向 BVM 的 UTXO 智能合约解释性执行系统设计与实现”。如果导师希望保留“高级语言”，可改为“面向 UTXO 智能合约高级语言的解释性执行系统设计与实现”。 |
| 摘要部分 | 摘要内容很完整，但单段过长，包含大量技术细节，如“97 个有效操作码”“RuntimeValue”“函数调用帧”“调试模块”等，阅读负担较重。摘要中对研究目的、方法和预期成果有说明，但“创新性成果”没有单独凸显。 | 培训材料第12页要求摘要简要说明研究目的、基本研究内容、研究方法、创新性成果及理论与实际意义，突出特色；第23页指出常见问题是摘要不能简明扼要归纳背景意义、研究内容和解决问题的技术方法。 | 建议将摘要压缩为3至4个自然段：第一段写背景和问题，第二段写主要工作，第三段写技术路线，第四段写预期成果与特色。保留“字节码解释、AST 解释、交易上下文、源码调试、差分测试”等核心信息，减少低层实现名词堆叠。 |
| 主题词：“区块链 智能合约 解释执行” | 主题词符合数量要求，但过于宽泛，未体现 UTXO、双栈虚拟机、BVM 或差分测试等报告核心对象。 | 培训材料第12页要求关键词能够准确概括全文核心内容，一般3至5个词。报告模板中提示“不多于三个”，因此更应提高关键词的识别度。 | 若保持三个中文主题词，建议改为“UTXO智能合约 双栈虚拟机 解释执行”或“UTXO智能合约 BVM 差分测试”。英文关键词相应改为“UTXO Smart Contract / BVM / Interpretive Execution”或类似表述。 |
| 1.1选题背景 | 背景从智能合约、账户模型、UTXO 模型、BVM 双栈虚拟机逐步展开，逻辑基本清楚。但工程来源仍偏隐含，报告只在封面列出实习单位，在正文中主要写“UTXO_Interpreter 工程载体已经具备基础形态”，没有充分说明该课题与实习单位、实际项目、用户需求或生产场景之间的关系。 | 培训材料第4页要求工程硕士论文选题直接来源于生产实际或具有明确工程背景，研究成果要有实际应用背景。第8页要求论证“这个选题应该进行研究”和“自己有条件进行研究”。 | 在1.1或1.2中增加“工程背景与应用场景”段落，说明本课题依托的工程载体、服务对象、开发痛点和可演示场景。若该课题确与实习单位项目相关，应据实写明；若不便写单位业务细节，也应说明其作为 UTXO 合约开发工具链的工程需求来源。 |
| 1.2工程设计价值意义 | 价值意义写了六点，覆盖本地执行、调试门槛、交易上下文、源语言运行时、安全性和工程平台，内容充分。但部分表述仍偏“功能价值”，对论文层面的理论意义、工程验收价值和应用收益之间的层次区分不够明显。 | 培训材料第13页要求首先阐明选题背景和选题意义；第10页要求体现专业性和逻辑性。 | 建议将意义分为“工程应用意义、技术方法意义、论文研究意义”三类。工程应用意义强调降低开发和调试成本；技术方法意义强调双路径解释和差分测试；论文研究意义强调为 UTXO 合约工具链提供可复现实验平台。 |
| 1.3国内外技术应用现状 | 已覆盖比特币脚本、EVM/Solidity、Move、sCrypt、Ivy、Simplicity、EUTxO、通用解释器和调试器等内容，具有一定综述意识。但正文没有在相应观点后标注参考文献编号，例如比特币、以太坊、Move、Simplicity、EUTxO、智能合约语言比较等均未见正文引用。 | 培训材料第14页要求国内外概况说明发展进程、研究方向、近年来发展趋势和最新成果；第15页要求参考文献引用要标注，体现阅读和综合分析能力；第22、23页均将参考文献引用处未标注列为常见问题。 | 在1.3中按研究类别加引用，例如比特币脚本处标注 Nakamoto 文献，以太坊/EVM 处标注 Buterin、Wood 和 KEVM 文献，Move 处标注 Move 文献，UTXO 高级语言和 EUTxO 处标注 Simplicity、Secure Compilation、Structured Contracts 等文献。建议每个关键判断至少对应1至2条引用。 |
| 1.3国内外技术应用现状 | 综述部分以叙述为主，比较维度还不够显性。例如 EVM、Move、sCrypt、Simplicity、EUTxO、通用调试器各自的“可借鉴点”和“不能直接替代本课题的原因”没有用表格或分层小结集中呈现。 | 培训材料第15页要求从大量文献中找到可借鉴内容，并对同行研究成果的优缺点作恰当评述。第23页指出背景偏离主题、介绍大背景而非自己相关问题是常见问题。 | 建议增加一张“相关工具与本课题比较表”，列出研究/工具、执行模型、支持能力、局限性、对本课题启示。这样可以更直接体现综述意识，并避免国内外现状沦为背景介绍。 |
| 1.4选题先进性和实用性 | 先进性从执行模型、交易上下文、源语言、验证方法四个层面展开，方向正确。但“先进性”和“创新点”边界不够清楚，部分表述仍是功能描述，如“维护主栈、副栈、PC、调用栈”等，尚未明确说明相对已有工作的改进点。 | 培训材料第14页要求通过与中外研究成果比较说明选题符合当前研究方向并有所进展，或采用当前最新技术并有所改进。第17页要求描述论文特色与创新点。 | 建议在1.4末尾增加“与已有工具相比，本课题的改进体现在……”的小结，明确写出差异：面向 UTXO 双栈语义、双路径解释一致性、交易上下文作为运行时一等数据、源码级调试与 BVM 栈状态映射。 |
| 1.5选题的技术难度和工作量；三、课题内容后的“技术难度及特色分析” | 技术难度写得较具体，符合培训材料“不应写自己没学过所以难”的要求。但1.5和后文“技术难度及特色分析”存在一定重复，均写双栈语义、交易上下文、运行时模型、调试映射、差分测试。 | 培训材料第16页要求技术难度和工作量应写项目本身的关键技术和难点，并估计大概工作量；第10页强调逻辑性。 | 建议分工：1.5侧重“为什么该选题达到工程硕士难度和工作量”，后文“技术难度及特色分析”侧重“具体方案中的关键技术突破”。可在1.5增加工作量拆分表，如模块、主要任务、预期代码或文档成果、验收方式。 |
| 三、课题内容及具体方案开头 | 报告有“本课题旨在……”和八项研究内容，但缺少单独的“研究目标”小节。目标散见于摘要、课题内容和核心问题中，不利于评审快速判断课题完成标准。 | 培训材料第10页概括开题报告要写“你要做什么、为什么做、如何做”；第18页要求首先说明课题内容，再说明设计方案和技术路线。 | 在“课题内容”前或后增加“研究目标”小节，写出总体目标和3至5个可验收目标，例如实现 BVM 字节码解释、实现 AST 源码解释、建立交易上下文模型、完成源码级调试、构建差分测试和评测体系。 |
| 三、课题内容第1至8项 | 研究内容具体，但多处使用“设计并实现”句式，内容之间有工程模块罗列感。当前没有明确区分“已有基础”“本论文拟完成工作”和“用于验收的成果”。例如报告已写工程载体具备 Lexer、Parser、AST、BVM 模拟器、CLI 调试器等基础，但课题内容部分没有区分哪些是复用、哪些是新增、哪些是完善。 | 培训材料第18页要求说明围绕选题准备做哪些方面工作，并说明设计方案、技术路线、方法和实验验证方案。 | 建议将八项内容整理为“已有基础、拟完成内容、验收指标”三列表。这样既能避免把已有系统能力全部写成本人研究内容，也能使工作边界更加清晰。 |
| 系统需求分析和概要设计部分 | 报告已包含功能需求、非功能需求、用例图、总体架构图、活动图、功能模块图和时序图，符合软件系统设计论文的基本方向。但功能需求多为自然语言，缺少需求编号和验收条件，后文测试方案也没有逐项回扣需求编号。 | 培训材料第4页要求工程软件论文需求分析合理、总体设计正确、程序编制及文档规范，并通过测试或可现场演示。第18页建议软件系统设计论文可用 UML 工具描述需求分析、概要设计、关键模块详细设计和算法模型。 | 建议将功能需求改为 FR-1 至 FR-6，非功能需求改为 NFR-1 至 NFR-4，并为每项需求补充“输入、输出、异常情况、验收方式”。测试方案中对应写“覆盖 FR-1、FR-2……”以增强可追踪性。 |
| 4.1开发方法、4.3测试方案 | 技术路线可执行性较强，已经写出“前端复用、字节码执行、AST 解释、交易上下文、调试器联动、差分测试”等流程。但缺少一张清晰的技术路线图或路线表，未把“方法、模块、输入输出、验证指标”对应起来。 | 培训材料第18页要求说明采用什么技术路线实现论文目标，用什么方法、算法、技术手段达到目标，最后给出实验验证或测试方案。 | 建议增加“技术路线表”：源码输入与前端分析、双路径解释、交易上下文注入、调试信息映射、差分比较、实验评估。每一步写明输入、核心方法、输出和验证方式。 |
| 4.3测试方案 | 测试方案覆盖构建验证、模块回归、解释执行验证、调试器验证和对比评测，方向正确。但目前指标仍偏概括，如“统计编译时间、解释执行步骤、字节码长度、错误检出率”，未说明样例数量、测试覆盖范围、成功判定标准和失败处理。 | 培训材料第9页要求做一些实验验证以证明技术可行性；第18页要求最后是实验验证方案或测试方案。 | 建议补充测试指标表，包括指令覆盖数、合约样例数、回归用例数、差分一致性判定项、错误定位准确率、运行性能记录方式。若当前数据尚未完成，可写“拟统计”而不虚构具体数值。 |
| “技术难度及特色分析”中的“本课题的特色主要体现在以下方面” | 该段写的是特色，但没有用“创新点”标题；且五点特色被压在一个段落中，辨识度不强。 | 培训材料第17页明确要求描述研究内容、论文特色与创新点；第10页要求体现复杂性、特色、难度和创新。 | 建议将该段独立为“论文特色与创新点”，分条写“创新点一、创新点二、创新点三”。考虑工程硕士论文属性，建议使用“工程创新点”或“应用创新点”，避免过度声称基础理论原创。 |
| 四、工作进度的大致安排 | 时间跨度较完整，从2026.04至2027.06。但阶段描述仍偏粗，如“掌握项目各模块具体的原理”“完成项目编码与测试工作”，没有明确每阶段对应的模块、文档、实验或论文成果。并且“部署好开发环境”安排在2026.09至2026.11，而前期已经进入调研和设计，时间顺序略显不合理。 | 培训材料第20页要求时间节点描述详细一些，不宜太粗，从调研到完成论文要有一定时间跨度。第22、23页将时间计划问题列为常见问题。 | 建议细化到月或双月，明确每阶段交付物：文献综述、需求规格、UML图、核心模块实现、测试用例、差分实验、性能评测、论文初稿、论文修改稿等。将“开发环境搭建”提前到2026.06至2026.07。 |

本课题拟采用“统一前端、双路径解释、上下文注入、调试映射、差分验证”的技术路线。

第一，统一前端阶段。系统读取 `.ct` 合约源文件后，完成导入解析、词法分析、语法分析、AST 构建和静态检查，为后续源码解释路径和字节码解释路径提供统一输入。

第二，双路径解释阶段。源码解释路径直接遍历 AST，并通过 RuntimeValue、RuntimeSlot、Environment 和 RuntimeContext 等结构维护变量、作用域、函数帧、内置对象和交易上下文；字节码解释路径则将编译产物交给 BVM 字节码解释器，按照主栈、副栈、程序计数器和指令语义逐条执行。
