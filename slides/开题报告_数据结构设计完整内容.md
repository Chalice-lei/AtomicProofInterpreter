# 3.3 数据结构设计

本系统名为 UTXO_Interpreter，主要使用 `.ct` 文本文件、JSON 文件和 JSONL 消息保存与交换数据，不使用关系型数据库保存业务状态。

数据处理流程为：用户向系统提交 `.ct` 合约源码和可选的交易上下文；系统完成编译或运行后，输出编译结果、调试信息或执行轨迹；调试服务运行期间，系统与可视化插件通过 JSONL 消息实时交换数据。

- `.ct` 合约源码：外部 → 系统；描述合约结构和执行逻辑。
- 交易上下文：外部 → 系统；提供函数参数、合约成员和交易数据。
- 编译结果：系统 → 外部；保存合约接口和生成的脚本数据。
- 调试信息：系统 → 外部；建立源码与执行位置的对应关系。
- 执行轨迹：系统 → 外部；保存执行过程和栈变化。
- JSONL 调试消息：双向；实现断点、单步执行和状态查看。

## 3.3.1 `.ct` 合约源码文件

`.ct` 文件是编译、运行和调试的主要输入。UTXO_Interpreter 读取文件后，获取合约的结构和执行逻辑。该文件包含以下内容：

- `import`：导入的标准库或其他合约文件。
- `Library`：库名称和库成员。
- `Contract`：合约名称和合约成员。
- 结构体：结构体名称、字段名称和字段类型。
- 构造函数：构造参数和初始化语句。
- 函数：函数名称、参数、返回类型和函数体。

## 3.3.2 交易上下文文件

交易上下文文件在合约运行前由 UTXO_Interpreter 读取，用于提供函数参数、合约成员和交易验证数据。系统可读取 JSON 或键值文本格式。其 JSON 文件的主要字段为：

- `params`：保存按参数名组织的入口函数参数。
- `self`：保存当前合约实例的成员字段。
- `bvm`：保存合约执行时所需的交易验证数据。
- `currentTx`：保存当前交易的输入和输出信息。
- `preTx`：保存前序交易的输入和输出信息。

`bvm` 对象包含以下字段：

- `version`：当前交易的版本号。
- `lockTime`：当前交易的锁定时间。
- `inputCount`：当前交易的输入数量。
- `outputCount`：当前交易的输出数量。
- `inputsHash`：所有交易输入的摘要。
- `unlockingInput`：当前输入使用的解锁数据。
- `outputsHash`：所有交易输出的摘要。

`currentTx` 和 `preTx` 中的交易字段包括：

- `inputs`：保存交易输入列表。
- `outputs`：保存交易输出列表。
- `txid`：前序交易的标识。
- `vout`：被引用的前序交易输出索引。
- `sequence`：交易输入的序列号。
- `unlockingInput`：交易输入的解锁数据。
- `value`：交易输出的金额。
- `lockingScript`：交易输出的锁定脚本。

## 3.3.3 编译结果 JSON 文件

合约编译成功后，UTXO_Interpreter 生成编译结果 JSON 文件，供接口查看、脚本调用和部署准备使用。该文件包含以下字段：

- `metadata`：记录编译器名称、版本、构建时间和源文件信息。
- `structs`：记录合约中各结构体的名称、字段和字段类型。
- `abi`：记录可供外部调用的函数名称、索引和参数定义。
- `lock`：保存锁定脚本的可读表示 `asm` 和十六进制数据 `hex`。
- `unlock`：记录各函数对应的解锁参数模板。
- `constructorParams`：记录合约构造函数的参数定义。
- `functions`：记录合约中的公开函数、私有函数和库函数信息。

## 3.3.4 调试信息 `.debug` 文件

启用调试信息输出后，UTXO_Interpreter 生成 `.debug` 文件。调试器通过该文件将执行位置定位到对应的源码行。该文件包含以下字段：

- `version`：记录调试文件的格式版本。
- `format`：标识该文件为 UTXO_Interpreter 调试信息。
- `sourceFile`：记录原始合约源文件的路径。
- `contractName`：记录当前合约名称。
- `pcToSource`：记录执行位置到源码位置的映射。
- `lineToPC`：记录源码行号到执行位置的映射。
- `instructions`：记录执行单元及其对应的源码位置。
- `functions`：记录函数名称、执行范围、参数和局部变量。
- `localVars`：记录所有局部变量的汇总信息。
- `variables`：记录全局变量及其索引。
- `scopes`：记录各作用域的名称、位置、执行范围和父作用域。

源码位置中，`file` 表示文件名，`line` 和 `column` 表示起始行列，`endLine` 和 `endColumn` 表示结束行列。

## 3.3.5 执行轨迹 JSON 文件

运行过程中，UTXO_Interpreter 可生成执行轨迹 JSON 文件，用于离线回放和分析各执行步骤前后的主栈、副栈变化。该文件包含以下字段：

- `version`：记录执行轨迹文件的格式版本。
- `format`：标识该文件为 UTXO_Interpreter 执行轨迹。
- `stackOrder`：说明栈元素的排列方向。
- `top`：说明栈数组中哪一端为栈顶。
- `debugInfo`：保存源文件、合约、行号映射和函数摘要。
- `source`：保存源文件名和按行拆分的源码。
- `bytecode`：保存按执行位置排列的脚本数据。
- `lifecycle`：记录栈元素的产生、移动和消费过程。
- `steps`：保存按执行顺序排列的逐指令轨迹。

`steps` 数组元素包含以下字段：

- `step`：当前执行步骤的序号。
- `pc`：当前执行步骤的位置。
- `instruction`：当前完整指令文本。
- `opcode`：当前指令的操作码。
- `operand`：当前指令的操作数。
- `source`：当前指令对应的源码位置。
- `functionName`：当前指令所属的函数名称。
- `mainStackBefore`：指令执行前的主栈快照。
- `mainStackAfter`：指令执行后的主栈快照。
- `altStackBefore`：指令执行前的副栈快照。
- `altStackAfter`：指令执行后的副栈快照。
- `effects`：记录当前执行步骤对栈状态的影响。
- `error`：记录当前步骤执行失败时的错误信息。

栈元素中，`index` 表示元素索引，`depth` 表示栈深度，`hex` 表示十六进制数据，`byteLength` 表示字节长度；`int`、`intString`、`ascii` 和 `elementId` 分别表示整数值、整数字符串、ASCII 文本和元素唯一标识。

## 3.3.6 实时调试 JSONL 消息

启动实时调试服务后，UTXO_Interpreter 逐行读取请求，并逐行返回响应或事件，以支持调试操作和状态查看。JSONL 消息包括请求、响应、事件和状态快照。

请求消息字段：

- `seq`：请求序号，用于关联对应响应。
- `command`：请求执行的调试命令。
- 命令参数：保存断点、表达式或作用域等命令专用数据。

响应消息字段：

- `type`：标识当前消息为响应消息。
- `request_seq`：记录该响应对应的请求序号。
- `command`：记录该响应对应的请求命令。
- `success`：表示请求是否执行成功。
- `body`：保存请求成功后返回的数据。
- `message`：保存请求失败时的说明信息。

事件消息字段：

- `type`：标识当前消息为事件消息。
- `event`：记录就绪、停止、结束或错误等事件名称。
- `body`：保存事件原因、状态快照或事件说明。

状态快照的主要字段为：

- `state` 和 `pc`：表示当前执行状态和执行位置。
- `instruction`、`opcode` 和 `operand`：表示当前指令及其操作码和操作数。
- `lineInstructions` 和 `lineInstructionSummary`：记录当前源码行对应的指令列表和摘要。
- `functionName`：记录当前函数名称。
- `source`：记录当前执行位置对应的源文件和起止行列。
- `range`：记录当前执行范围的起止位置。
- `instructionCount` 和 `totalInstructions`：记录已执行指令数和指令总数。
- `mainStack` 和 `altStack`：保存当前主栈和副栈快照。
- `callStack`：保存函数调用层级、返回位置和栈基址。
- `warnings`、`lastEventMessage` 和 `error`：记录警告、最近事件说明和错误信息。
